晚饭做好了，博客新功能也有了初稿

Simon Willison 做饭时用语音指挥 Codex 开发博客 newsletter 归档功能，主要工作约半小时；之后打字审查和修改又用了约半小时（本人记录）。

谁·场景
开发者 Simon Willison 想给自己的 Django 博客加一个 newsletter 归档页。他熟悉这个代码库，功能范围也明确。
怎么用
他在 ChatGPT 桌面版的 Codex 里先打字让它启动本地开发服务器、打开预览，再开语音对话。笔记本放在厨房，他边做饭边口述需求，隔着厨房看预览，口头纠正。
结果
约半小时，语音阶段完成了数据模型、四个导入脚本、归档页面和站内搜索集成。接着用 PR 审查，把一个导入脚本从 Git 子进程改成 API 调用，又打字约半小时后上线。
你可以试
挑一个你熟悉、边界清楚的小功能或内部工具，先开好预览，再口述需求。记时间时把审查和修改也算进去。
注意
他本人说这不会成为日常主力方式：到了细节，粘贴报错和示例比口述更有效率。这种做法也不适合开放式办公室。

Simon Willison 在本人博客记录了这次开发：用 ChatGPT 桌面版 Codex 的语音模式，对着本地开发环境做出 Newsletters 页面。他公开的口述稿充满「嗯」和自我纠正，比如先说不想让 newsletter 出现在日期归档页，又改口说要出现。模型照样理解了需求。语音阶段约半小时，做出数据模型和迁移、四种导入（包括从 Substack 未公开的 API 翻页抓取）、公开归档页和搜索集成。

他的工作顺序可以借鉴：先打字启动预览 → 语音讲清目标和例外情况 → 让 Codex 开分支、提 PR → 坐回键盘审查。审查时他发现一个导入脚本用 Git 子进程拉私有仓库，就改成了 API 方式，并补上调整。这部分又用了约半小时。

他说的主要好处是能同时做两件事，原来做饭时听播客的时间，现在可以用来开发。前提是本人懂代码、能判断 PR 质量，任务也足够小。他也写明，细节阶段还是打字更快。
