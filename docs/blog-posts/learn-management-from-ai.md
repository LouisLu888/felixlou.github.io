## 一、私董群里的问题

接着上次，继续点播回答私董群里的问题。

这次的问题大意是：**怎么才能把一件事真正交出去？** 布置的时候简单交代一下，收回来发现完全不是想要的；再讲一遍，还是差一层；来回两轮，干脆自己做了——反正自己做还快些。

我的答案有点绕：先别翻管理书。先看看你自己是**怎么给 AI agent 布置任务的**。

---

## 二、两个 prompt

同一件事，两种交代方式。

给 agent：花二十分钟写 prompt。目标是什么、产出给谁看、什么算做完（三条可判定的标准）、哪些明确不做、不确定时的默认选择是什么。最后加一句：先输出执行计划和你识别到的最大不确定，等我确认再开始。

给人：「你去看一下这个，下周给我。」

![两个 prompt：给 agent 的一整页交代，和给人的一句话](/images/ai-management/fig-01.svg "右边那一大片空白，就是这篇文章的全部论点。")

这不是懒。二十分钟的 prompt 写得心甘情愿，一句话的口头交代也说得毫无负担。差别在于两套默认假设：

- 对 agent，默认它不会自动理解，所以一切必须显式化；
- 对人，默认他应该懂，所以显式化显得多余，甚至像不信任。

Agent 的价值不只是替你干活。它是一个不会体谅你的对照组——人会在你没说清楚的地方用 judgment 帮你补上，然后把成本自己吞掉；agent 会用统计学补，然后把结果直接甩回你脸上。

所以它是一面镜子：你在 prompt 里做得毫无心理负担的那些事，恰恰是管理里最该做、却最常被省略的那些事。

下面三件可以直接搬过来，三件搬不过来。搬不过来的那三件，才是你雇人的理由。

---

## 三、可以搬的三件事

### 1. 上下文是编译，验收是 eval

给 agent 写 prompt，第一课是上下文不足会产生幻觉，第二课是上下文过载同样致命——三十页会议纪要全塞进去，关键约束就淹没在噪音里。

![上下文是编译：从一堆原始材料压缩成对方能直接执行的形式](/images/ai-management/fig-02.svg "上下文不足会产生幻觉，上下文过载会淹没关键约束。")

管理者在两端都翻车：

- **只给动作不给背景。** 你说「调研三个 vendor」，他交回三个 vendor 的对比表。但你要的是「下周三决策会上能选定，并且我信任这个选择」。
- **把我知道的都告诉你。** 转发一堆邮件、拉进十个群，「你看一下就懂了」。这不是给上下文，是把理解成本转嫁出去。

上下文不是共享，是编译。你要把脑子里那些从没成文的判断——为什么是现在、上次为什么没做成、哪个人的反对其实不用太当真——压缩成对方能直接执行的形式。筛选标准只有一条：**只给会改变他选择的信息。**

编译的另一半是验收标准。

要让 agent 稳定工作，你迟早要写 eval：必须先定义什么叫做对了，否则无法判断，也无法迭代。而交给人的任务，大部分从来没定义过验收，全靠交付之后一句「感觉不太对」。

> 「感觉不太对」不是评价，是当初没写验收标准的账单，最后由执行的人来还。

以前这一步能靠「我看到就知道」糊过去。现在你被迫要为 agent 写 eval，这个能力缺口第一次变得可见。

### 2. Plan mode：最便宜的管理动作

用 agent 的人都知道，最划算的一步是让它先出计划，你确认，再执行。成本几乎为零，收益极高——你在它跑掉两小时之前就抓住了走偏。

![检查点的位置：在 20% 进度处确认方向，而不是在交付日](/images/ai-management/fig-03.svg "检查点放在进度的 20%，看最丑的那版东西。")

同样的动作落在人身上，叫让他先复述目标、给出方案，再开工。

那为什么在人身上很少做？因为有心理阻力：「这么简单还要确认一遍，显得我不信任他」「他会不会觉得我在查岗」。

而你对 agent 完全没有这种负担。

这值得停三秒：挡住这个动作的不是方法，是管理者的社交羞耻。Agent 把管理动作去道德化了，你才看清哪些动作本来就该做。

操作上，检查点放在进度的 20%，看最丑的东西：一段伪代码、一个 outline、一张手画草图。只问三个问题：

- 用你自己的话说一遍这个任务的目标。
- 你打算怎么做？
- 现在最大的不确定是什么？

第一问抓走偏，成本接近零，回报最大。

一条纪律：这个阶段不评价质量。你一挑细节，下次他就不敢给你看粗稿了——然后你只能在 deadline 当天看结果。

### 3. 权限模型：两个维度，别用一个覆盖另一个

这是我从 agent 设计里拿到最有用的一条。

![权限按操作配置，而不是按执行者配置](/images/ai-management/fig-04.svg "你信任一个 agent，不等于你允许它 rm -rf。")

**第一个维度看事：可逆性 × 影响半径。**

你不会对 agent 的所有操作都要求确认。读文件 auto-approve，写临时文件 auto-approve；删生产数据、发布线上、给客户发邮件——manual approval。分界线的依据不是任务难度，不是重要性，而是出事之后能不能回滚，以及炸多大。

|  | 影响小 | 影响大 |
|---|---|---|
| **可逆** | 直接做，不用报 | 做了同步我一声 |
| **不可逆** | 做了同步我一声 | 必须等我拍板 |

**第二个维度看人：情境领导。**

同一个 agent，跑熟悉的任务你放开 auto-approve，跑没试过的新场景你会盯着每一步。模型没变，任务变了，管理模式就变了。人也一样——管理模式是「能力 × 意愿」的函数：

- 能力低、意愿高（新手上路）→ 给方法。讲清楚怎么做，别怕细。
- 能力低、意愿也低（撞过墙、正在幻灭）→ 给方法 + 给理由 + 陪一段。这时候只给目标等于放弃他。
- 能力高、意愿不稳（会做但没底气）→ 别给方法，给信心和参与决策的机会。这时候教方法，等于告诉他你不信任他。
- 能力高、意愿高 → 给目标、给资源、走开。

最容易犯的错，是把这两个维度混着用。

一种是因为信任某个人，就在所有事情上放手，包括不可逆、高影响的操作。工程上你绝不会这么干：你信任一个 agent，不等于你允许它 `rm -rf`。权限是按 tool 配的，不是按 agent 配的。

另一种是给人贴固定标签（「他是资深的」「他是新人」），然后在所有任务上用同一档模式。但同一个人，在 A 任务上是老手，在 B 任务上可能完全是新手。

> 授权是「人 × 这件事」的函数，不是「人」的函数。

最后补一句常被漏掉的：agent 没有对应的工具就干不了活，它要么报错，要么编个假数据继续跑。人也一样——没给数据权限他就凭印象估，没引荐关键的人他就绕路两周。布置任务的同时，必须一起交付执行它所需的访问权。

## 四、搬不过来的三件事

只讲相似，这就是个噱头。分界线在哪，才决定这套类比可不可信。

### 1. 积累的形态：一个是基础设施，一个是手艺

![积累的两种形态：可复制的基础设施，和带得走的手艺](/images/ai-management/fig-05.svg "一个属于公司，一个属于他自己。")

Agent 的记忆是工程问题。上下文没了就重新给，你用 RAG、memory 文件、prompt cache 去解决。它外部、显式、可复制——搭好了换个模型也能立刻用上。它是基础设施，属于公司。

人身上积累的完全不是这个形态。人积累的是手艺和品味：他能在说不出理由之前就闻出一个方案不对，他知道哪种客户的哪句话必须当真。这些写不进文档，复制不了，要很多年，而且属于他自己，随时可以带走。

管理含义很硬：因为品味无法用文档传递，培养人的方式就不能是「讲清楚」。

品味只在一个地方长出来——他自己做了判断，然后拿到了反馈。你把 spec 写得越完整、判断空间留得越小，他执行得越准，手艺长得越慢。

所以管得极细的管理者，效率往往真的很高，同时也在稳定地阻止手艺形成。这是一笔看不见的账。

而当 AI 把标准执行的成本压到接近零，品味恰好是那个还在涨价的东西。

### 2. 情绪：它不是 bug，是你的信息通道

![情绪与信息通道：被当众否定一次之后，汇报开始自动美化](/images/ai-management/fig-06.svg "你不是在管一个玻璃心的人，你是在管自己的信息质量。")

Agent 没有情绪。跑挂了重跑，成本是 token，你可以毫无顾虑地说「这里错了，重做」。

人会玻璃心。而管理者最常见的误判，是把这件事归结为「这个人不够专业」。

但情绪成本是真实的系统成本，它最终结算在信息流上：一个人被当众否定一次，代价不是他当天不高兴，是接下来三个月他不再给你看粗稿、不再第一时间报坏消息、汇报开始自动美化。

你收到的世界从此是被过滤过的。你不是在管一个玻璃心的人，你是在管自己的信息质量。

所以两件事必须显式做：

- **反馈时先归因**：是我 spec 写错了，还是执行偏了？给 agent 不需要区分，给人必须区分。归因错误的代价，agent 是零，人是长期的。
- **提前授权求助**：「卡住超过 N 小时就来找我，这不算失败，这是流程。」不说出来，人的默认策略是硬扛，扛到你发现时已经两周了。

反过来，情绪也是 agent 永远拿不到的资源。人有 pride、有 ownership，会为了做出一个自己骄傲的东西较劲。Agent 不 care 结果好不好。

### 3. 主动性：默认状态是相反的

![主动性的默认方向：agent 需要被授予，人自带但极易被管没](/images/ai-management/fig-07.svg "对 agent 是激发，对人是不要破坏。")

这是最大的一个不同。

Agent 的 agency 是你授予的。边界完全由 prompt 定义，它不会主动越界，也不会在你没问的地方发现问题。你要写很多字，才能把它的行动空间扩大一点。

人的 agency 是自带的。他会在你没布置的地方看见问题，会在下班路上还想着这件事，会绕开一个你根本没意识到的障碍，会主动多做一步。

所以管理的动作方向是反的：对 agent 是激发，对人是不要破坏。

而它极其容易被破坏，方式都很日常：任务布置得过于完整，一点判断空间都没留；他主动做的事没被看见，或者换来一句「谁让你做这个的」；反馈只在出错的时候出现。

> 如果团队交回来的东西总是刚好等于你写下的要求，那不是执行力强，是 agency 已经被管没了。

## 五、一张总表

| 维度 | 给 agent | 给人 | 管理动作 |
|---|---|---|---|
| **上下文** | 给全，但不能过载 | 默认「他应该懂」→ 事故起点 | 只给会改变他选择的信息 |
| **验收** | 必须写 eval，否则无法迭代 | 全靠「感觉不太对」 | 交代时就列 2–3 条可判定标准 |
| **计划** | 先出 plan 再执行，成本近零 | 觉得「再确认显得不信任」 | 20% 进度看最丑的稿 |
| **权限** | 按 tool 配，不按 agent 配 | 常按资历一刀切 | 事看可逆性，人看能力 × 意愿 |
| **积累** | context infrastructure，可复制 | 手艺与品味，带得走 | 留判断空间，否则手艺不长 |
| **情绪** | 没有，失败重跑即可 | 会玻璃心 | 先归因再反馈；提前授权求助 |
| **主动性** | 你授予多少才有多少 | 自带，且极易被管没 | 不是激发，是不要破坏 |

## 六、结论

![输入与输出的两套标准](/images/ai-management/fig-08.svg "输入端向 agent 看齐，输出端向人看齐。")

用 agent 的标准要求自己的输入，用人的标准期待对方的输出。

输入端向 agent 看齐——显式、完整、可判定、边界清楚、授权分级。这些事你在 prompt 里做得毫无心理负担，就说明它们本来就不是「不信任」，只是过去不好意思。

输出端向人看齐——期待判断、期待手艺、期待他主动折腾出你没要求的东西。

Agent 不会替代管理者。它只是把管理里那些一直靠人默默补上的部分，第一次变成了显式的、可测量的。
