01｜旁路 Agent 提醒他：还有 45 个文件的改动没提交

谁·场景
AI 工程师 Dan McAteer，过去几周在个人项目里用 Claude Mods 改造自己的 Claude Code 工作流。
怎么用
Mod 是一段 TypeScript/JavaScript 插件，挂在提交 prompt、调用工具、界面渲染这些事件上，可以改动展示内容，也可以接管默认行为。他开启了内置的 You Should Know，又自己做了一个 Next Steps Supervisor。
结果
有一次主 Agent 改完界面文案、截了前后对比图，看上去已经完工。You Should Know 这时提醒他：被改的文件和另外约 45 个文件里都有没提交的旧改动，丢弃这次修改会把它们一起丢掉，建议先 commit 或 stash。
你可以试
用 Claude Code 的人可以运行 /plugin，在 Installed 的 Built-in 里打开默认关闭的 You Should Know。也可以直接用大白话让 Claude 写一个 mod，它内置了写 mod 的技能。
注意
提醒太多会被忽略。按 README 的估算，每次检查在 5 万 token 的会话上约消耗 5 到 6 千输入 token，缓存过期后更多。Mod 是在 Claude Code 里运行的代码，装别人写的之前要先审查。

Dan McAteer 在 Latent Space 的文章里介绍了他这几周怎么用 Claude Mods。Anthropic 在 Claude Code 里内置了 6 个 mod，大多在后台运行。他开启了 You Should Know：一个旁路 Agent 观察主 Agent 干活，把埋在执行记录里、又会影响结果的决定挑出来告诉你。前面那次没提交的 45 个文件，就是它发现的。

他自己写的 Next Steps Supervisor 放在开源插件 ModSmith 里。只要某一轮改了文件、执行了命令或调用工具达到 8 次，它就复查一遍，列出值得注意的点，再给出一个可以直接点的下一步按钮。他拿另外两种做法对比：ChatGPT 的 Intelligent UI 由模型决定界面，Cursor 的 PR Routing 由团队写规则来分配审查。Mods 则是用户和 Claude 一起决定人的注意力该花在哪。

问题出在触发条件。他从 10 月 15 日装上，111 轮里有 99 轮都触发了，不少提醒只是噪音，他开始跳着看。自己写 mod 时，触发条件要收窄：只在删除文件、改动范围大这类高风险时刻提醒。

02｜按故事点付工程师工资，这家 AI 交付公司做到 75 人

谁·场景
应用 AI 服务公司 Tenex 的联创 Alex Lieberman 和特别项目负责人 CJ Hess，在 AI Engineer 纽约大会上接受 Latent Space 访谈。
怎么用
工程师按故事点拿报酬。负责客户的 AI strategist 要为续约和增长负责，所以会拒掉对客户没用的需求。交付时用 MetaHarness：把技能、项目文档和计划决策跟代码一起提交到 Git。
结果
Alex 说公司有 75 人。最初是 AI 开发外包，现在越来越多客户请他们帮整个公司做 AI 转型。他说，大家担心的虚报估点、交烂代码刷点数，至今都不是最大的问题。
你可以试
如果你接 AI 开发的活，可以试试按交付物报价，并把计划、验收标准和决策记录放进代码仓库，让 Agent 回来接手时知道当初为什么这么做。
注意
Tenex 自己承认，这么多结构对一个人做一个项目来说太重。理解需求、设计架构这类工作没法写成一张工单，按点付费的制度还得另外给它们留出位置。

CJ Hess 在这期节目里讲了他加入 Tenex 的原因：以前他按小时给客户计费，用上 AI 以后产出更快更好，挣的钱反而少了。Tenex 按故事点付钱，双方事先约定每项工作值多少点。Alex 说，这样一来工程师之间的收入差距会比以往任何时候都大。CJ 说，模型越强，他直接写代码的时间越少，更多时间花在把客户的背景整理成模型能用的形式。

MetaHarness 的思路是让写代码以外的工作也有据可查。计划、验收标准、决策和证据都留在仓库里，再接到 Linear、GitHub 和给客户的进度更新上。Alex 对团队的说法是："一个不存在的流程，没法自动化。"

节目还谈到 Latent Space 自己的 Kill My SaaS 实验：为了替换一个报价每年 4.3 万美元的讲者管理工具，他们收到 72 份方案。人类评委选出的冠军，在 AI 评委的榜上只排第 19。Alex 提醒，自己做的工具也得有人一直维护。做咨询的人可以借这个问题判断交付范围：客户省下的费用，够不够付后续维护的钱？

03｜Cursor 设计师 Ryo Lu：别让 Agent 替你跳过难的那段

谁说的
Ryo Lu 曾在 Cursor、Notion、Stripe 做设计，也自己创过业。他在 X 上发了一篇长文。
核心观点
他认为 AI 让人不必弄懂原理就能拿到结果。结果看着完整，人就容易漏掉那些从没学会去问的问题。Agent 总在、总有耐心，跟它说话比找一个可能误解你、反对你的人更轻松。
依据
依据是他的亲身经历：修不好的 bug、看着对但用户一用就出问题的设计，让他慢慢练出了没法说清却能察觉不对劲的直觉。他最亲近的一些朋友，也是一起熬过难关的合作者。他也说，用这些工具做出了一些原本可能永远做不出来的东西。
对你的意义
学一项新技能时，可以留一部分问题先自己啃，再去问 AI。遇到卡住的设计或方案，先拿给同事看半成品，别第一时间只找 Agent。
争议·条件
这是一篇个人反思，没有数据。他自己也说，吃苦本身不会让东西变好，有些苦本来就没人该受。

Ryo Lu 在这篇长文里讲了自己的学习方式：读半懂的资料，把东西拆开看，向人求助，推倒重来。很多作品做得并不好，但做过足够多轮以后，有些东西就留了下来，变成他思考方式的一部分。他担心的是，人还没弄明白难点教会了自己什么，它就已经被 AI 拿掉了。

另一层担心在协作。和人一起工作不舒服：每个人想要的不一样，有人在你觉得无关紧要的细节上较真。可磨合下来，团队会像乐队一样，知道谁能发现你漏掉的东西。他还提醒，每个人和自己的 Agent 待在各自的小世界里，而这些世界跑在公司的服务器上，受到我们看不见的利益影响。

这对带新人的管理者和正在转型的人都有用。用 AI 把繁琐的活干完，把能锻炼判断力的难题留给自己，并且有意识地保留和同事一起讨论半成品的时间。

今天可以做的一件事

打开你最近一个用 AI 写代码或写文档的项目，在根目录建一个 decisions.md，补三条最近做过的关键决定：做了什么、为什么这样做、怎么验收。下次让 AI 接手这个项目时，先让它读这个文件。用 Claude Code 的人还可以运行 /plugin，打开 You Should Know，用一周，记下它提醒了几次、其中有几次真的有用，再决定留不留。
